### 存储与同步规范（文件为唯一真相源）

这份规范的目标很简单：**永远不要出现 FeelFish 那种“软件缓存和文件不同步”的蠢问题**（参考： [FeelFish Documentation](https://www.feelfish.com/en/docs) ）。  
结论：**文件是唯一真相源（SSOT）**，SQLite 只是索引/加速读模型，随时可重建。

---

### 1. 文件格式硬规则（作者已确认）

- **正文（章节内容）必须是 `.txt`**
  - **UTF-8 纯文本**
  - **禁止由系统生成 Markdown 语法**（标题/列表/粗体/代码块等）
  - 目标：作者可用 Cursor 直接编辑，内容不会被格式噪声污染

- **其他产物必须是 `.md`**
  - Story 大纲、段落计划、设定抽取报告、审校报告、风格约束、trace 摘要等
  - 目标：结构化信息用 Markdown 表达更可读、更可审阅

> 说明：这里的“禁止 Markdown 语法”是针对**系统自动写作/润色输出**的格式约束；如果作者刻意在正文里写 `#` 作为剧情元素，不应被系统擅自修改。

---

### 2. SQLite 的定位（只加速，不当真相源）

- **SQLite 只做**：
  - 全文检索索引（章节/设定/审校报告）
  - 快速过滤与统计（字数、章节状态、近似重复）
  - 实体引用关系图（人物/地点/势力/道具 → 出现在哪些章节）

- **SQLite 不做**：
  - 不作为正文/大纲的唯一存储
  - 不承诺单独读取 SQLite 就能还原全部内容（必须以文件为准）

- **一致性原则**：
  - 任何时候 SQLite 与文件冲突：**文件赢**
  - SQLite 必须可通过“全量重扫项目目录”重建

---

### 3. 实时同步（反应文件变更的唯一正确方式）

- **监听范围**：项目根目录下所有资产文件（`.txt` + `.md` + 未来的元数据文件）
- **监听策略**：
  - 使用文件系统监听（去抖/合并短时间多次写入）
  - 以“最终落盘内容”触发解析与索引更新（避免读取半写入状态）
- **冲突处理（最小原则）**：
  - 如果同一资产在 UI 内写入时外部也被修改：产生新 revision，并给出可视化 diff，让作者决定

### 3.1 偏离资产（从 diff 提炼作者意志）

- **定义**：当作者在修改“AI 初稿”时产生偏离，系统把偏离视为最高信号（作者意志），并产出一组可回放的派生资产。
- **输出（均为派生，可删可重建）**：
  - **偏离摘要（`.md`）**：总结“AI 初稿 → 作者改稿”的关键变化（剧情/人设/语气/信息密度等）。
  - **一键提示词/指令（`.md`）**：把偏离压缩成可直接投喂给 AI 的指令，用于检查并联动后续内容。
  - **影响分析与备用方案（`.md`）**：扫描后续大纲/章节/设定库，给出需要修改的位置与多套方案。
  - **结构化偏离条目（Protobuf）**：同一份偏离会被拆成分类条目（剧情/人设/语气/信息密度/设定/时间线/节奏…），便于 ImpactPlanner 做精确扫描（不替代文件真相源）。
- **一致性原则**：
  - 这些派生文件永远不能反向覆盖正文真相源；作者最终决定只能通过“修改正文/大纲文件”体现。
  - SQLite 仅索引这些派生资产，任何不一致以文件为准。

### 3.2 写作日志（按会话聚合）

- **定义**：把一段连续写作过程当成一个“会话”，聚合该会话内的关键事件，帮助作者复盘与掌控全局。
- **会话边界（v1）**：
  - 默认自动：根据编辑活动与时间间隔聚合（实现层做去抖/合并，不在这里绑定具体分钟数）。
  - 支持手动：作者可显式开始/结束一次会话（适合重要重写/大改动）。
- **输出（派生，可删可重建）**：
  - **会话写作日志（`.md`）**：包含偏离摘要、闸门决策、单元测试结果、影响分析、采纳的方案与路线图。
  - **作者意志提示词（`.md`）**：从会话日志抽取的可复用指令，用于驱动后续章节/大纲联动更新。
- **关键原则**：
  - 日志是“作者意志的时间轴”，不替代正文与大纲；正文/大纲仍然是 SSOT。

### 3.3 故事单元测试产物

- **测试定义（`.md`）**：作者定义故事规则/约束（可版本化），作为“可回归”的质量闸门。
- **测试报告（`.md`）**：每次生成/改稿后自动产出，必须包含：失败定位（哪里拽歪）+ 原因 + 修复建议（可选路线图）。
- **一致性原则**：测试只给建议与定位，不做“偷偷改正文”；任何修复必须落到正文/大纲文件。

### 3.4 伏笔台账（Setup/Payoff Ledger）

- **SSOT（作者可编辑）**：
  - `artifacts/ledger/setup_payoff_ledger.md`
- **派生（可删可重建）**：
  - `artifacts/ledger/reports/<run_id>_setup_payoff_report.md`
- **一致性原则**：
  - 台账是“读者期待/承诺/债务”的结构化镜子，**不能反向覆盖正文**；任何兑现/升级/推迟都必须落到正文/大纲，并同步更新台账。

---

### 4. 性能直觉（500 万字规模）

- **5,000,000 字**量级的纯文本正文，本质上是几十 MB 级别的数据量；  
  - **文件可读并不会天然拖慢**，关键在于：按章节分文件、按需加载、增量索引。
  - SQLite 的价值主要在“搜索/过滤/引用关系”，而不是替代正文文件存储。
