### 0. 一句话愿景

做一个**面向网络小说创作全流程**（讨论剧情 → 设定抽取 → 大纲 → 章节写作 → 自动润色 → 一致性校验 → 迭代重写）的“**可组合多智能体写作系统**”：  
前端用 **Tauri + React** 提供极强可用性；后端用 **.NET sidecar（Aevatar Agent Framework）** + **Cognitive Mesh DSL** 把创作流程建模成可编排、可追溯、可度量的智能体网络。  
对标 FeelFish 的核心体验（Agent、Smart Context、Intelligent Book Breakdown、提示词管理等），但重点解决其“提示词与工程架构薄弱、记忆与调教差”的问题（参考： [FeelFish Documentation](https://www.feelfish.com/en/docs) ）。

### 0.1 产品理念（写作的主体性）

- **AI 让故事更严密、更精巧**：它能把复杂度抬到“非天才也能掌控”的高度——冲突结构、伏笔回收、时间线自洽、设定引用一致性，都可以被系统化地做到极致。
- **但永远不要放弃自己去实现这个故事**：写作不是把结果外包给机器，而是通过“写作与输出”完成自我——这是作者的不可替代性。
- **AI 产出永远被视为初稿**：
  - 初稿可以达到发布标准，但仍然只是“第一层可用版本”。
  - 作者拥有最终裁决权：你可以接受、重写、删改、偏离——系统只负责让这些决策更轻、更快、更可回放。
- **协商不是打断创作，而是训练创作**：流水线允许全自动跑完 `Story`，也允许在每个关键节点停下；停下的每一次协商，都是把“作者意志”写回作品的过程。

### 1. 产品定位与边界

- **产品定位**：写“长篇网络小说”的生产力系统，不是单次聊天写作工具。
- **核心承诺**：
  - **确定性**：任何关键产出可追溯到输入/上下文/决策链（event log + trace）。
  - **一致性**：角色、世界观、时间线、伏笔前后一致（规则 + 记忆检索 + 校验代理）。
  - **可组合**：用户可以像搭积木一样组合工作流（Cognitive Mesh DSL）。
- **作者驱动（你已确认）**：
  - **题材/目标/节奏不预设**：由作者提示词与项目约束决定（系统负责把约束“结构化”并强制执行）。
  - **默认全自动流水线**：可以在任何中间产物节点插手协商/修改，然后“一键继续”。
  - **可配置跳过协商**：作者可提前设置策略，让 AI 自动跑到某个 `Story` 结束（或直到书完结）。
  - **模型走 API Key**：先做“预算不设上限”的版本，后续再加作者自定义预算上限/配额。
- **非目标（首期不做）**：
  - 多人实时协作编辑（后续可做）
  - 复杂版权/出版排版全链路（先聚焦创作内核）

### 2. 关键功能（对标但不抄）

- **项目管理**：
  - Novel / Volume / Story / Chapter 层级管理（`Story` = 剧情大纲，书内可包含多个 Volume，每个 Volume 包含多个 Story）
  - 版本（Revision）与分支（Rewrite Branch）管理
- **剧情讨论（对话式）**：
  - 以“议题”组织：冲突、节奏、爆点、爽点、伏笔、转折
  - 输出结构化结论：可直接落入大纲与设定库
- **设定抽取与知识化**：
  - 从已有文本/资料抽取：人物卡、势力、道具、世界规则、时间线、地点、关系网
  - 冲突检测：同名异物/设定矛盾/时间线自洽
- **智能拆书 / 学习风格（可选）**：
  - 输入参考文本（TXT）→ 提炼：叙事风格、句式偏好、节奏模型、常用修辞、视角习惯
  - 生成“风格约束”而不是堆提示词（参考： [FeelFish Documentation](https://www.feelfish.com/en/docs) ）
- **参考文本设定抽取 / 世界观融合（新增核心能力）**：
  - 仅支持 TXT 输入（未来扩展 EPUB 等）
  - 从 TXT 中抽取“设定包”：世界规则、术语体系、力量体系、社会结构、关键实体（人物/势力/地点/道具）等
  - 支持“条件化融合”：`TXT + 提示词约束` → 生成融合设定  
    - 例：给《哈利波特》TXT → 抽取魔法世界设定  
    - 例：给《庄子》TXT + “修仙世界”提示词 → 抽取“庄子思想 + 修仙世界”的融合设定
- **写作与润色**：
  - 章节生成：按大纲分镜/段落计划生成
  - 自动润色：语病、节奏、对白、信息密度、情绪曲线
  - 多目标重写：更爽、更快、更克制、更文艺、更悬疑
- **流水线控制（关键体验）**：
  - 暂停点（Pause Points）：在大纲/段落计划/初稿/润色/审校等节点可“停下协商”
  - 自动继续（Auto-Continue）：按策略跳过暂停点，直跑到 `Story` 结束
- **偏离驱动的联动改写（新增核心能力）**：
  - 目标：系统**重点读取作者在改稿过程中的每一次偏离**，把偏离当成最高信号（作者意志）而不是“噪声”。
  - 偏离摘要升级为“结构化条目”：按**剧情/人设/语气/信息密度/设定改动/时间线/节奏**等分类组织，方便精确扫描后续牵连。
  - 一键生成“变更意图提示词/指令”：让 AI 对照偏离，检查**后续章节 + 后续大纲 + 时间线 + 设定库**是否需要联动调整。
  - 输出“备用方案”：给作者多套可选策略（保守修补 / 激进重写 / 调整大纲回收方式），作者一键采纳或继续偏离。
- **故事单元测试（Narrative Tests，新增核心能力）**：
  - 作者为自己的故事写“规则/约束”（例如：信息揭示顺序、设定限制、人物动机前后一致、时间线不跳跃）。
  - 每次生成/改稿后自动运行：失败时直接给出**定位（哪里拽歪）+ 原因 + 修复建议**。
  - 单元测试不是要束缚创作，而是让作者敢于重写：改一处，立刻知道后面会崩在哪些点。
- **写作日志（按会话聚合，新增核心能力）**：
  - 系统自动把一次写作会话中的“改稿偏离/闸门决策/单元测试结果/影响分析/采纳的方案”聚合成可读日志。
  - 日志可一键生成“当前作者意志提示词”：用来驱动后续章节与大纲的联动更新。
- **故事仪表盘（Story Control Panel，新增核心能力）**：
  - Volume/Story/Chapter 进度
  - 未回收伏笔清单（来自伏笔台账）
  - 人物出场/关系网（实体图谱）
  - 力量体系/规则引用热度（设定引用统计）
  - 时间线冲突警报（连续性/因果自洽检查）
- **伏笔台账（Setup/Payoff Ledger）**：
  - 所有“埋点/承诺/债务”结构化记录
  - 自动提示“该回收了 / 被你改稿破坏了 / 可升级为爆点”
- **设定引用与变更治理（Canon Governance）**：
  - 设定变更必须显式记录：变更原因/影响范围/是否追溯改前文
  - 防止“设定泥石流”：变更可审计、可回放、可回滚、可分支
- **分支与合并（Rewrite Branch / Merge）**：
  - 把“重写路线”当成一等公民：多方案并行写作、对比、择优合并
  - 让作者敢于重写：不怕把主线写崩（随时回滚/切换路线）
- **读者视角模拟（Reader Personas）**：
  - 不同读者画像对章节的“爽点/困惑点/信息负荷”评分与解释
  - 帮作者精确控制阅读体验（不是迎合，而是明确取舍）
- **上下文/记忆系统（核心差异点）**：
  - Smart Context：自动从项目资产生成上下文（角色/设定/前文摘要/未回收伏笔）（参考： [FeelFish Documentation](https://www.feelfish.com/en/docs) ）
  - “记忆不是聊天记录”：分层、可检索、可校验、可衰减、可手工编辑
- **提示词管理（但不依赖提示词堆砌）**：
  - Prompt 作为“可版本化资产”，与工作流节点绑定
  - 有评测与回归机制（prompt 变更必须过基准样例）
- **评审与质量闸门**：
  - 一致性评分、复读/注水检测、人物口吻一致性、设定引用正确率

### 3. 总体架构（Tauri + React + .NET Sidecar + Aevatar + Cognitive Mesh）

#### 3.1 进程/边界

- **Frontend（Tauri + React）**：
  - 编辑器、项目资产浏览、工作流画布/DSL 编辑、运行与回放、对话与审校面板
- **Sidecar（.NET 10）**：
  - Aevatar Agent System（multi-agent）
  - Cognitive Mesh（DSL 解析/编排/执行）
  - 记忆/索引/事件溯源/评测

#### 3.2 跨边界契约（铁律）

本仓库硬性要求：**任何跨越边界的类型必须用 Protobuf 定义**（State、Event、Configuration、通过 Stream 传输的消息、Event Sourcing 事件）。  
因此：

- **所有 Agent State**：`.proto` 定义并生成
- **所有 Event Messages**：`.proto` 定义并生成
- **所有 Workflow Node 配置**：`.proto` 定义并生成
- **UI ↔ Sidecar**：建议用 gRPC/HTTP（传输 DTO 也必须 protobuf 或明确本地不跨边界；这里默认跨边界 → protobuf）

#### 3.3 存储与同步（文件 SSOT + SQLite 只做索引）

- **文件是唯一真相源（SSOT）**：
  - 写作资产（章节正文/大纲/评审/风格等）以**可读文件**形式落盘，任何时候以文件内容为准。
  - Sidecar/UI 不维护“会漂移的缓存副本”；最多只维护**可重建**的派生索引/摘要。
- **格式规定（你已确认）**：
  - **正文（章节内容）一律用 `.txt`**：UTF-8 纯文本，**生成与自动润色必须避免输出 Markdown 格式语法**（标题/列表/粗体/代码块等）。
  - **其他中间产物与文档一律用 `.md`**：大纲、段落计划、审校报告、风格约束、运行 trace 摘要等。
- **SQLite 的角色**：
  - 用于全文索引、快速筛选、实体引用关系、时间线查询等“加速读”能力。
  - SQLite 永远是派生读模型：**可删可重建**；一旦与文件不一致，**文件赢**。
- **实时反应文件变更（核心体验）**：
  - Sidecar 必须监听项目目录变更（作者用 Cursor/外部编辑器改文件也能立刻同步到 UI/Agent）。

### 4. Multi-Agent 设计（职责分离，不堆 if/else）

#### 4.1 核心代理（第一批）

- **OrchestratorAgent（编排/指挥）**：
  - 解析用户意图，选择/启动 Cognitive Mesh 工作流
  - 做成本/质量/时延权衡（模型选择、上下文裁剪）
- **LoreKeeperAgent（设定守护）**：
  - 维护设定库（人物/势力/规则/道具）
  - 提供“设定引用 API”，并对写作结果做引用校验
- **CanonGovernanceAgent（设定治理）**：
  - 负责设定变更的“申请/理由/影响/追溯策略”记录与审批闸门
  - 触发影响扫描（哪些章节/大纲/伏笔台账需要联动修改）
- **TimelineAgent（时间线）**：
  - 维护事件时间轴、章节发生顺序、因果链
- **OutlineAgent（大纲）**：
  - 负责：Arc/Chapter 大纲生成、冲突结构、伏笔回收计划
- **SetupPayoffLedgerAgent（伏笔台账）**：
  - 维护“埋点/承诺/债务”结构化条目（Setup/Payoff）
  - 发现破坏/缺失/可升级爆点，并给出回收路线图
- **DraftWriterAgent（写手）**：
  - 生成初稿（按段落计划/镜头表）
- **EditorAgent（润色）**：
  - 语言质量、节奏、对白、信息密度；支持多目标改写
- **DeviationAnalyzerAgent（偏离分析）**：
  - 对照“AI 初稿 vs 作者改稿”提炼偏离点（作者意志的结构化表达）
  - 一键生成“变更意图提示词/指令”（用于后续一致性扫描与联动改写）
- **ImpactPlannerAgent（影响规划/备用方案）**：
  - 扫描后续大纲/章节/设定库，找出需要联动修改的区域
  - 给出多套备选方案（最小修补 / 大纲调整 / 伏笔重布 / 章节重写建议）
- **NarrativeTestAgent（故事单元测试）**：
  - 执行作者定义的“故事规则/约束”，把失败定位到具体章节/大纲/设定条目
  - 给出修复方向（最小修补 vs 大纲重排 vs 伏笔回收调整）
- **WritingJournalAgent（写作日志/会话聚合）**：
  - 聚合一次写作会话的关键事件（偏离/决策/测试/采纳方案）并落盘为可读日志
  - 从会话日志抽取“作者意志提示词”，供后续联动改写复用
- **StoryDashboardAgent（故事仪表盘）**：
  - 聚合进度/警报/热度/台账/测试结果，输出 Story Control Panel 的可视化数据
- **BranchManagerAgent（分支与合并）**：
  - 管理 rewrite branch（创建/切换/对比/合并/回滚），并把合并决策事件化
- **ReaderPersonaAgent（读者画像模拟）**：
  - 以多读者画像对章节输出评分与解释（爽点/困惑/信息负荷），给作者可选优化路线
- **ConsistencyCriticAgent（审校）**：
  - 发现矛盾、设定偏离、人设崩坏、重复啰嗦
- **StyleAgent（风格）**：
  - 从参考文本抽象风格约束并持续施加
- **MemoryAgent（记忆/检索）**：
  - 管理分层记忆、索引、检索与上下文拼装（Smart Context）

#### 4.2 实现方式建议：Agents vs Skills vs Tools vs DSL（选型结论）

结论：**用 Multi-Agent 承担“长期职责 + 持久状态 + 审计”，用 Skills 承担“可复用 SOP/提示词模板”，用 Tools 承担“真实动作执行”，用 Cognitive Mesh DSL 承担“流程编排”。**

- **用 Agent 实现（推荐）**：当能力需要“长期维护状态/资产”，或需要“事件化审计/回放”，或需要“并行协作”：
  - Story Control Panel（指标聚合）、Setup/Payoff 台账、Canon Governance、Branch/Merge、Timeline、Lore、Tests、Journal、Persona 结果聚合
- **用 Skill 实现（强烈推荐配套）**：当问题本质是“流程/规范/评分 rubric/提示词模板复用”，并希望按需加载：
  - 伏笔台账撰写规范、设定变更审批规范、读者画像评分 rubric、故事单元测试编写模板、合并策略模板
  - 技术上：在对应 `AIGAgentBase` 开启 `EnableAgentSkills=true`，并挂载 `novel/agent_skills` 作为 root（见仓库 `docs/AGENT_SKILLS_GUIDE.md`）
- **用 Tool 实现（必须）**：当需要做“读写文件/SQLite 索引/生成 diff/图谱计算/合并算法”等真实动作：
  - 推荐优先做成**宿主侧 C# 工具**或 **dotnet-file tool**，再让 Skill 规定调用方法与参数规范
- **用 DSL 编排（必须）**：把上面的 Agent/Tool 串起来，形成可配置工作流（A/B/C/D/E/F/G/H/I/J），并允许暂停/继续/回放

#### 4.3 事件驱动与传播

- **向下传播（Down）**：编排者将任务广播给子代理（写作/抽取/审校）
- **向上传播（Up）**：子代理将发现/结论发布到父级流，形成“群体共识”
- **双向（Both）**：需要同步收敛的任务（比如矛盾修复回合）

### 5. Cognitive Mesh DSL：把“写作流程”变成可组合的图

#### 5.1 DSL 建模原则

- **节点 = 纯职责**：一个节点只做一件事（抽取/写作/审校/重写/打分）
- **边 = 数据流**：显式声明输入输出（禁止隐式共享大对象）
- **状态 = 资产化**：产出落入资产库（设定、摘要、大纲、章节草稿、评审报告）

#### 5.2 典型工作流（首期提供模板）

- **工作流 A：剧情讨论 → Story 大纲落库**
  - 用户议题输入 → 冲突结构生成 → 反转/爆点建议 → 形成 Story/Chapter 大纲 → 保存
- **工作流 B：导入既有文本 → 设定抽取/冲突检测**
  - 文本切分 → 角色/地点/规则抽取 → 知识合并 → 矛盾报告 → 人工确认 → 入库
- **工作流 D：参考 TXT → 设定抽取/融合 → Canon 入库**
  - 导入 TXT →（可选）融合提示词 → 抽取“设定包（md）+ 结构化条目（proto）”→ 人工确认/修订 → 入 Canon Memory
- **工作流 E：作者改稿偏离 → 影响分析 → 备用方案（可一键继续）**
  - 捕获作者偏离（diff）→ 偏离摘要（md）→ 一键生成“变更意图提示词/指令”（md）→ 扫描后续大纲/章节/设定 → 影响分析与备用方案（md）→ 作者采纳/修改 → 一键继续流水线
- **工作流 F：故事单元测试 + 会话写作日志（Phase 1 核心）**
  - 文件变更/改稿发生 → 运行故事单元测试 → 输出失败定位与修复建议 → 触发工作流 E（可选）→ 聚合写作会话日志（md）→ 作者一键继续/分支重写
- **工作流 G：伏笔台账构建/回收路线图**
  - 扫描 Story 大纲/已写章节 → 生成/更新 Setup/Payoff 台账 → 标记未回收/被破坏/可升级爆点 → 输出回收路线图（含分支建议）
- **工作流 H：设定变更治理（Canon Governance）**
  - 提交设定变更（理由/影响/追溯策略）→ 扫描后续影响（章节/大纲/台账/时间线）→ 给出修复路线图 → 作者审批 → 一键继续
- **工作流 I：Rewrite Branch 对比/合并**
  - 创建分支 → 并行写作 → 对比分支（差异/测试/读者画像）→ 选择合并策略（择优段落/择优章节/保留双线）→ 合并落盘
- **工作流 J：读者画像模拟（Reader Personas）**
  - 选定章节/故事段 → 多画像评分（爽点/困惑/信息负荷）→ 生成可选优化路线（保守/激进/爽点强化/信息降噪）
- **工作流 C：章节写作 → 自动润色 → 一致性闸门（可暂停/可自动继续）**
  - 段落计划 → 初稿 → 润色 → 一致性校验 → 不过闸门则触发重写回路 →（可选）自动继续到 Story 结束

### 6. 记忆系统（为什么 FeelFish 体验差，我们怎么赢）

参考 FeelFish 的“Context / Smart Context / Agent”概念（见： [FeelFish Documentation](https://www.feelfish.com/en/docs) ），但我们把它工程化：

- **记忆分层**：
  - **Canon Memory（硬设定）**：不可随意改写；变更需显式事件（审计）
  - **Working Memory（当前章节工作区）**：短期、可衰减
  - **Derived Memory（派生结论）**：摘要、风格约束、人物口吻模型、**作者偏离意图（Author Intent from Diffs）**
- **索引与检索**：
  - 结构化检索（按实体/字段）
  - 语义检索（向量）
  - 规则检索（时间线/因果/设定依赖）
- **上下文拼装（Smart Context）**：
  - 以“任务类型”驱动上下文：写作/润色/审校需要不同上下文
  - 有预算：token/成本/时延三维约束
- **可编辑**：
  - 用户能直观看到“AI 使用了哪些记忆片段”，并能锁定/排除

### 8. 分阶段里程碑（可执行）

#### 8.1 Phase 0：对齐骨架（1-3 天）

- **定义数据资产模型**：Novel/Volume/Story/Chapter/Entity（人物/地点/规则/道具）
- **定义 proto 契约**：状态、事件、工作流配置
- **确定侧车通信**：Tauri ↔ sidecar 的 API 形态（HTTP/gRPC）

#### 8.2 Phase 1：最小闭环（1-2 周）

- **工作流 C（章节写作闭环）**：
  - 段落计划 → 初稿 → 润色 → 评审 → 保存版本
- **工作流 E（偏离 → 联动建议）v1**：
  - 作者改稿后，一键生成：偏离摘要 + 变更意图提示词 + 后续大纲/章节联动建议（含备用方案）
- **故事单元测试（Narrative Tests）v1**：
  - 支持作者定义最小规则集，并在每次生成/改稿后自动运行
  - 输出：失败定位（哪里拽歪）+ 修复建议（含可选路线图）
- **写作日志（按会话聚合）v1**：
  - 自动聚合一次写作会话内的关键事件：偏离/测试/影响分析/采纳方案
  - 输出：会话日志（md）+ 可复用的“作者意志提示词”
- **故事仪表盘（Story Control Panel）v1**：
  - 最小可用：进度 + 单元测试结果 + 偏离/影响分析入口 + 时间线冲突警报（先做硬错误）
- **最小 UI**：
  - 章节编辑器 + 运行工作流按钮 + 结果对比（diff）
  - 故事单元测试面板（失败定位/修复建议）+ 会话写作日志面板（偏离/决策/路线图）
  - 故事仪表盘面板（进度/警报/入口）

#### 8.3 Phase 2：设定抽取与一致性（2-4 周）

- **工作流 B（导入/抽取/冲突）**
- **工作流 D（参考 TXT → 设定抽取/融合）**
- **LoreKeeper + Timeline + ConsistencyCritic** 三件套
- **伏笔台账 v1 + 设定治理 v1**
- **Smart Context v1**：写作/润色/审校三类上下文模板

#### 8.4 Phase 3：剧情讨论与大纲系统（2-4 周）

- **工作流 A（讨论 → 大纲）**
- **Arc/Chapter 可视化**：卡片化结构、冲突曲线
- **Rewrite Branch/Merge v1 + Reader Personas v1**

#### 8.5 Phase 4：评测与回归（持续）

- 建立基准样例：同输入产出质量稳定、可回归
- prompt / 模型 / 上下文策略变更都必须过基准

### 9. 技术风险与原则（先把坑写在纸上）

- **模型不稳定**：用“评测 + 闸门 + 重写回路”对冲
- **上下文膨胀**：用预算与分层记忆，禁止把全书塞进提示词
- **一致性难**：用结构化设定 + 时间线 + 引用校验代理，而不是靠“让模型记住”
- **工程复杂度**：坚持“节点单一职责”，消灭 3+ 分支的逻辑膨胀
